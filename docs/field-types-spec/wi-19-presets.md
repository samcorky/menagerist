# WI-19a to WI-19c: Reusable presets (saved fields, field groups, lists)

> Part of the field-types spec. Read `00-INDEX.md` and `01-context-and-conventions.md` first (skip the second if this is that file).
> **Depends on:** WI-14 and WI-20; WI-10 (in-use warning when updating options). WI-19d is a separate file.
> "WI-n" refers to `wi-*.md` files listed in `00-INDEX.md`; "open question N" refers to `open-questions.md`.


**Goal.** Let users save field definitions once and reuse them: single fields, named sets of fields (for example "Purchase details": price, date, shop, condition) and choice lists. A saved item can be added to a node type or, later, to a single item, and can be exported and imported as a pack. Partly modelled on Koillection's templates.

**Terminology (decided).** The existing `group` field kind is a table of repeating rows, so its **UI label becomes "Table"** (the `label` on its descriptor; the code name stays `group`). That frees "Field group" for a named collection of fields, which is the user-facing name; in code and in stored definitions it stays `field_set`, so it never clashes with the `group` kind. The Settings page is **"Saved fields"**, with three sections: Fields, Field groups and Lists.

**Vocabulary used in this spec.** *Item type* (UI; `node type` in code): the definition items are created from. *Template* (reserved for later): a whole starter item type, such as "Vinyl". *Preset* (code and this spec): a reusable part, shown to users as a **saved field**, **field group** (`field_set` in code) or **list** (`choice_list` in code). *Pack*: an importable and exportable bundle of presets or item types.

## Comparison with Koillection

From Koillection's wiki. Those pages are sparse and mostly dated 2022 to 2023, and they say nothing about choice lists or newer field types, so check the running app before copying anything beyond this table.

| Koillection | Menagerist today | Proposal |
|---|---|---|
| Metadata is added per item as typed fields: Text, Number, Country, Date, File; image kinds Image and Sign | Fields are defined per node type; per-item extras are untyped loose details (WI-18) | Keep schema-per-type. Typed per-item fields only through the optional WI-19d. |
| Templates "automatically add fields to your items", and you can apply a template while creating an item | Nothing equivalent | Field sets (WI-19b), applied to a node type; per-item application in a limited form |
| On an item you can load common fields based on other items in the same collection, or load the fields of the collection | Nothing equivalent | "Copy details from another item" (WI-19b) |
| Collections carry custom fields too | No collection-level fields; the node type is the closest concept | Not mirrored |
| A Country field offers a list of countries | Choice with hand-typed options | Built-in "Countries" choice list (WI-19c) |
| File, Image and Sign fields | Media module, with a single well-known `cover` slot (see `further-field-types.md`) | Future kinds |
| Tags, wishlists, loans, visibility and sharing, scraping (in progress), API | Tags exist; the rest is out of scope | Not part of this spec |

## Decision: copy on apply, with provenance (v1)

- Applying a saved field, set or list **copies** its definition into the node type's schema with fresh keys generated by WI-20. A node type's schema therefore stays a standalone JSON Schema that both validators can use, and deleting a preset never breaks a type.
- The copy records where it came from: `x-menagerist.origin: { "preset": "<id>", "version": <n> }` on each property created. Provenance is metadata only and never affects validation. It enables an "update available" hint later without coupling.
- Live links (edit a list once and every type updates) are a v2 idea: a `SyncChoiceList` command that rewrites the options of every referencing type, validating each and using the WI-9/WI-10 usage counts before removing an option that is in use. I could not confirm from the wiki whether Koillection templates propagate later edits.

## Preset entries

Stored as JSON definitions. Common columns: `id` (uuid7), `kind`, `label`, `description`, `definition` (JSONB), `version` (int, bumped on every edit), `builtin` (bool), timestamps, soft delete.

- `field`: `{ "property": { ...one key-less JSON Schema property with x-menagerist... } }`.
- `field_set`: `{ "section": "Purchase details", "properties": [ ...ordered key-less properties... ] }`. Applying assigns fresh keys and adds the properties to the layout under a section named after the set.
- `choice_list`: `{ "options": ["Mint", "Near Mint", "VG+"] }`, ordered.

## WI-19a: preset core (save and add fields and choice lists)

- **New backend module `presets`** (decided: its own module) with its own hexagonal layers, not coupled to `graph`. It only stores and serves definitions; applying one is done by the client: fetch the definition, insert it into the node type's schema, then use the existing ETag-protected `PATCH /node-type/{id}`. No cross-module calls, and the architecture tests must still pass.
- **Use cases:** `CreatePreset`, `GetPreset`, `ListPresets` (filter by kind, `q`), `UpdatePreset` (bumps `version`), `DeletePreset` (soft).
- **Endpoints** (singular prefix like the others): `POST /preset`, `GET /preset`, `GET /preset/{id}`, `PATCH /preset/{id}` (conditional), `DELETE /preset/{id}`.
- **Persistence:** a new `preset` table with an Alembic migration (this is the first migration in this spec), a SQLAlchemy adapter and an in-memory sibling.
- **Save for reuse** ("Save as preset" in code and this spec): from a field in the schema editor (a `field`), from a choice field's options (a `choice_list`), and from a per-item custom detail (WI-18; kind inferred from the value's shape). Saved copies drop keys, `origin`, highlights and layout positions.
- **Add from saved fields:** in the schema editor, "Add from saved fields..." with search, kind filter and preview; a choice field gets "Use a saved list", which copies the options in and records `origin`. The choice field shows "From list X (v3), update available" when the preset's version is newer, with an "Update options" action that warns about in-use values (WI-10).
- **Management page:** "Saved fields" at `settings/saved-fields`, next to the existing item type and relationships pages (the item type page is still `settings/categories` until the rename in `01-context-and-conventions.md` happens).
- **Relabel the Group kind as Table** in the schema editor's kind picker and any docs (`group.ts` descriptor `label`; the code name stays `group`).

## WI-19b: field sets, ad hoc use and copying details

- **Field groups:** "Save selection for reuse" (select several fields, or a section, in the schema editor) and "Add from saved fields" for groups, which creates a section in the layout.
- **Ad hoc, per item:** applying a field group to a single item adds its fields to that item's own schema (the WI-19d overlay, decided), so they keep their kinds, and it offers "Add these to <item type> instead".
- **Copy details from another item:** on the item form, choose an item (same type by default) and copy its custom detail **names** (not values), like Koillection's "load common fields based on other items".

## WI-19c: packs, import and export, built-ins

- **Format:** `{ "format": "menagerist-presets", "version": 1, "items": [ ... ] }`. Endpoints `GET /preset/export?ids=` and `POST /preset/import` (use cases `ExportPresets` and `ImportPresets`). Import creates new items with new ids and never overwrites; it reports created and skipped, and importing the same pack twice must not create duplicates (dedupe by content hash or by provenance; open question 30).
- **Node types** can travel in the same envelope (schema, label, description) so a "Vinyl" type can be shared. That overlaps the roadmap's import/export goal, so scope it there.
- **Imports are untrusted data:** shape and size limits, unknown kinds preserved as `opaque` (WI-4), patterns must pass the portable-subset check (WI-15), and strings are rendered as text, never as HTML.
- **Built-in packs (optional):** read-only entries (`builtin = true`) shipped with the app, for example Book, Movie, Vinyl and Comic field sets and the choice lists Condition grades, Countries and Languages. They help first-run and double as example fixtures. Seeding mechanism (startup sync or migration): open question 31. Later, plugins could contribute packs that also carry enrichment mappings (TMDB, MusicBrainz, books).

## Interactions

- WI-14: `origin` is a new property member; `schema-meta` accessors read and write it. Export and import use the same accessors.
- WI-8: an archived field can still be saved as a preset from the editor's "Removed fields" list.
- WI-15: saved fields carry their constraints; imports run the portable-subset check.
- WI-16: highlights are per type and are not part of a saved field or set.
- WI-18: "Save for reuse" and "Make this a field" (18b) are neighbouring actions on the same custom detail.

**Acceptance.**
- A field saved from one type can be added to another type with fresh keys, keeps its kind, options and constraints, and records `origin`.
- Editing a preset bumps its version; a type that copied the previous version shows "update available" and can update its options after an in-use warning.
- A field set adds a labelled section with all its fields.
- Exporting then importing a pack on a clean database reproduces the items; importing it twice creates no duplicates; a malformed or oversized pack is rejected with a clear message.
- A built-in item cannot be edited or deleted.

**Tests.**
- Unit: definition validation for each kind; copy-with-provenance (fresh keys, `origin`, dropped highlights); version bump; import/export round trip; import hardening (unknown kind, bad pattern, oversized pack).
- Integration `I-9` (real Postgres): JSONB round trip of definitions, `builtin` protection, idempotent import, soft delete, migration test for the new table.
- Contract fixture: a pack fixture shared by both suites.
- End-to-end: save a field as a preset, add it to another item type, see it on a node.
