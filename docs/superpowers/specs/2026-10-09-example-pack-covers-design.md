# Generated covers for example packs

**Status:** design agreed in conversation on 2026-10-09; awaiting written-spec review. No code yet.
**Scope:** backend (examples module, a cover renderer, a bridge to media) and pack content. No frontend code: items already show their cover wherever one is set.

## Purpose

The example packs' cards and lists look plain because no item has a picture. The content is deliberately fictional (no real titles, people or companies), so real covers or stock photos are not an option. Each example item that has a natural cover gets a **generated** one, drawn at install time and removed with the pack.

## Decisions (owner, 2026-10-09)

1. **Generated covers**, not hand-made illustrations and not photographs: no licensing, almost no repo or image size, a distinct cover per item.
2. **Only item types with a natural cover** (record, film, board game, recipe). People, venues, gigs, shops, brands and parts stay plain. Each pack file marks which of its item types have covers.
3. **Raster images** (PNG drawn with Pillow, already a dependency), not SVG: the media module treats SVG as unsafe content and thumbnails come from raster images. Drawing is deterministic, seeded from the item's name, so a reinstall gives the same cover.
4. **Covers are their own removable entity** in the install record, so a pack's own cover does not count as the user's file.

## Behaviour

- **Pack format:** version 3, additive (versions 1 and 2 still load). An item type may carry `"cover": {"style": "<name>"}` where the style is one of a small closed set: `sleeve` (square, records), `poster` (tall, films), `box` (landscape-ish, board games), `card` (recipes). An unknown style is a parse error. The parser stays strict.
- **Install:** after items are created, each item whose type has a cover style gets a generated cover attached through the media module and set as its cover image. Failures roll back like every other install step.
- **Look:** a background colour chosen from a hash of the item's name (from a fixed, accessible palette), a simple shape per style, and the item's first letter large. Text is never longer than one character, so no font or language problems.
- **Size:** each cover is a small PNG (target under 20 KB); thumbnails are generated by the existing media pipeline.
- **Removal:** covers are settled first, before connections, collections and items. A cover is removed if it is still the one the pack made. If the person replaced or deleted it, that is their change: a replaced cover stays with its item (and so the item is kept, as it is today for any file the person added); a deleted cover is simply gone.
- **Reinstall after keeping things:** a kept cover is re-adopted with the kept item (the same rule as other kept entities, using the original content hash). If the item was adopted but its cover was removed, a fresh cover is created.
- **User-facing counts:** covers are not a count in "3 item types, 14 items" and never appear in kept-reason messages as a noun; an item kept because it has the person's own cover uses the existing "has your connections, files or collections" reason.

## Structure

- `examples` module: `EntityKind.COVER`, placed first in `REMOVAL_ORDER`; a `CoverRenderer` port (`render(name, style) -> bytes`) with a Pillow adapter in the examples module's adapters; a `CoverTarget` port (`create(item_id, name, style) -> Created`, `inspect`, `remove`) beside the other targets in `ports/pack_targets.py`.
- Bridge in `entrypoints/api/shared/example_targets.py` implements `CoverTarget` with the media use cases (upload and attach, set cover, detach and delete). The examples module still does not import media, graph or collections (architecture test unchanged).
- The recorded content of a cover is `{style, name, sha256 of the generated bytes}`, so "edited" means the stored asset is no longer the one we drew.

## Testing

- Parser: version 3 with and without covers, unknown style, cover on an unknown type.
- Renderer: deterministic (same input, same bytes), different names give different covers, valid PNG within the size target for every style, non-ASCII first letters.
- Install, uninstall and re-adoption use cases with in-memory targets: cover created for covered types only, removed on uninstall, replaced cover keeps the item, deleted cover does not block removal, kept cover re-adopted, failure mid-install rolls covers back.
- Postgres integration through the real media storage for one pack.
- E2E: install Movies, film items show a cover; remove Movies, covers and items go; install, replace a film's cover, remove: the film and its replaced cover stay; reinstall re-adopts it without duplicating.
