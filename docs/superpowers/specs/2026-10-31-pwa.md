# Menagerist — Progressive Web App (PWA)

**High-Level Design** · Version 0.2 · Draft · 31 October 2026 · corrected against the code

## 1. Purpose

Make Menagerist feel as close to a native installed application as practical, while preserving its SvelteKit frontend, FastAPI backend, and self-hosted deployment model. Deliver improvements in small, independently useful stages. Offline domain data and synchronisation are deliberately deferred.

### Goals
- Installable on Android, iOS and supporting desktop browsers.
- Standalone presentation, excellent touch UX, safe-area handling and platform-aware navigation.
- Instance-specific branding through a dynamic manifest.
- Useful camera, share and shortcut integrations where supported.
- Safe, predictable updates and secure caching.
- Architecture ready for future offline data and sync without implementing them prematurely.

### Non-goals (initial release)
- Offline editing, optimistic write queues, conflict resolution or background sync.
- Native app store packaging, Capacitor or separate mobile codebase.
- Guaranteed parity of OS integrations across browsers.
- Caching authenticated API responses or private media in a service worker.

## 2. Context and architecture

**Verified frontend:** SvelteKit 2/Svelte 5, `@sveltejs/adapter-static`, generated `200.html` SPA fallback, Vite development `/api` proxy, and the viewport/theme bootstrap in `frontend/src/app.html`. There is no manifest, service worker, `viewport-fit=cover` or `theme-color` yet, and `frontend/static` holds only SVG favicons and logos and `robots.txt` (no PNG icons).

**Verified backend:** FastAPI (Granian) serves the built frontend; there is no Nginx (a stale comment in `svelte.config.js` still mentions it). `app/entrypoints/api/spa.py` defines `SpaStaticFiles`, mounted at `/` last in `application.py` so every API route wins. Its rules: `_app/immutable/*` is cached for a year; other real files for an hour (`max-age=3600`); a missing path that looks like an asset (a dot in the last segment) is a real 404; dotfiles except `.well-known` are 404; unknown `/api/*` is 404; everything else gets `200.html` with `Cache-Control: no-store` and an explicit CSP (`default-src 'self'`, `script-src 'self' 'unsafe-inline'`, `img-src 'self' blob: data:`, `connect-src 'self'`). `SecurityHeadersMiddleware` fills API defaults with `setdefault` (CSP `default-src 'none'`, `Cache-Control: no-store`, `Permissions-Policy` with `camera=()`, `Referrer-Policy: no-referrer`), so a new route must set its own CSP and cache headers.

```text
Browser / installed PWA (same origin)
  ├─ SvelteKit UI and client-side routing
  ├─ /manifest.webmanifest  ────────────┐
  ├─ /service-worker.js (built asset) ──┤
  ├─ /api/* ────────────────────────────┤
  └─ /* (SPA routes, JS/CSS/assets) ────┤
                                        ▼
                                 FastAPI / Granian
                                  ├─ API routes and auth
                                  ├─ public dynamic manifest route
                                  ├─ frontend static asset serving
                                  ├─ SPA fallback: generated 200.html
                                  ├─ instance settings (when available)
                                  └─ PostgreSQL
```

**Routing constraint:** a dynamic `/manifest.webmanifest` must be registered on the app before the `/` mount (the mount is last, so any earlier route wins). `.webmanifest` and `service-worker.js` both look like assets, so the existing 404 rule already stops them falling through to the shell. Two gaps in `spa.py` need changes: a built `service-worker.js` would be served with the one-hour asset cache, so it needs `Cache-Control: no-cache` (and `Service-Worker-Allowed` only if the scope must widen); and a static `manifest.webmanifest` would also get one hour, which is acceptable for Stage 1 but not once branding is editable.

**Development vs production:** Vite proxies `/api` during local development; production uses FastAPI directly, not a proxy. Do not add a separate frontend server merely for PWA support.

Keep domain state on the server. Introduce a dedicated PWA integration layer in the frontend rather than mixing platform checks throughout components.

## 3. Delivery stages

**Implementation order:** Stage 0 → Stage 1 → Stage 5 (service worker) → Stage 3 (mobile polish) → Stage 2 (dynamic branding) → Stage 4 (device integrations) → Stage 6 (optional). Existing stage numbers are retained for traceability; the numbered PWA implementation slices below reflect the recommended execution order.

Each stage must be shippable without the next stage.

### Stage 0 — Audit and mobile foundations

**Outcome:** existing web app is pleasant on phones before installation is introduced.

- Audit mobile navigation, viewport sizing, dialogs, keyboard focus, form controls, tap targets and photo-first quick capture.
- Use `viewport-fit=cover` and CSS `env(safe-area-inset-*)` where edge-to-edge layouts require it.
- Respect reduced-motion, font scaling, light/dark preference and accessibility.
- Ensure deep links, back navigation, browser refresh and auth redirects work in the SPA.
- Confirm HTTPS and the public origin (`MENAGERIST_API_PUBLIC_ORIGIN`, which also drives `cookie_secure` and the proxy-configuration readiness check); localhost is a development exception.

**Already in place:** the app shell has a mobile drawer with a focus trap and scroll lock, a bottom bar using `env(safe-area-inset-bottom)`, `pointer-coarse:` tap targets, and a viewport meta that already sets `interactive-widget=resizes-content`. The audit starts from there; `viewport-fit=cover` is only needed where an edge-to-edge layout calls for it.

**Acceptance:** core browse, search, create, edit, capture and sign-in flows work at common phone widths without horizontal overflow or hidden controls.

### Stage 1 — Installable PWA baseline

**Outcome:** Menagerist can be installed and launched in a standalone window.

- Add manifest link, appropriate icons (including maskable artwork), theme color and display mode.
- Provide `name`, `short_name`, `id`, `start_url`, `scope`, `display: standalone`, background/theme colors and icons.
- Register a minimal service worker if needed for desired browser/install behaviour; do not add offline API caching.
- Handle standalone display mode and iOS home-screen metadata.
- Provide contextual install guidance; do not assume `beforeinstallprompt` exists (not available on iOS).
- Keep normal browser usage fully supported.

**Acceptance:** supported Android and desktop browsers can install; iOS users can add the site to Home Screen; launch uses correct identity and scope. Installation criteria vary by browser.

### Stage 2 — Dynamic instance manifest and branding

**Outcome:** each self-hosted instance can advertise its own application identity without rebuilding frontend assets.

**Recommended contract:** a public, same-origin FastAPI `GET /manifest.webmanifest` endpoint, registered before the SPA mount and backed by a public instance-branding projection. SvelteKit is statically built and has no runtime server endpoints. The use case declares `access = Public` (pinned in `tests/architecture/test_access_stances.py`), and the route sets its own `Cache-Control` and `Content-Type: application/manifest+json`, because the middleware default is `no-store`. Branding values would be `Tunable()` settings on a settings group, editable on the existing admin settings page, rather than a new mechanism.

Proposed backend-owned public settings:

| Setting | Example | Notes |
|---|---|---|
| app display name | `Sam's Menagerist` | Configurable instance label |
| short name | `Menagerist` | Compact home-screen label |
| description | `Personal collection manager` | Optional |
| theme/background colours | Valid CSS colours | Validate and normalise |
| icon references | Same-origin versioned URLs | Provide PNG sizes and maskable variants |
| app start path | `/` | Prefer stable, non-user-specific path |
| scope | `/` | Keep within app origin and deployment base path |

**Manifest identity:** use a stable `id` independent of mutable display name or start URL. For per-instance installation, prefer a stable root-relative identity scoped to each origin. For path-hosted multi-instance deployments, include a stable instance-specific path in the identity and scope. Changing `id` can create a second installed app rather than update the first.

**Privacy:** manifest is public. Never embed tokens, usernames, collection data, internal addresses or secrets. Do not derive public URLs from untrusted `Host` or forwarded headers; use the validated `MENAGERIST_API_PUBLIC_ORIGIN` setting.

**Caching:** serve manifest with a conservative revalidation policy (`Cache-Control: no-cache` or short max-age plus ETag). Browsers/OSes may not immediately refresh installed-app metadata after changes. Serve icon URLs with content hashes or revisions when branding changes.

**Validation:** restrict icon uploads to supported image formats, validate sizes, strip unnecessary metadata, and provide generated/default fallbacks. Use safe same-origin URLs.

**Acceptance:** instance branding changes are reflected in the manifest without rebuilding the frontend; installed-app metadata refresh limitations are documented.

### Stage 3 — Native-feeling mobile UI

**Outcome:** the installed app feels designed for touch rather than a desktop site squeezed onto a phone.

- Define mobile navigation patterns (bottom navigation for frequent destinations; contextual actions for detail pages).
- Make system back and in-app back predictable; avoid duplicate history entries and accidental exits.
- Polish loading, empty, error, retry and session-expired states.
- Ensure dialogs, sheets and forms respond well to on-screen keyboards.
- Use native-feeling scrolling, pull-to-refresh only if it does not conflict with OS/browser gestures, and touch feedback.
- Use view transitions sparingly with reduced-motion support; do not animate every route by default.
- Consider status-bar and theme-color changes with platform support limitations.

**Acceptance:** installable app navigation, forms, capture and detail screens pass manual Android/iOS UX checks.

### Stage 4 — Device integrations

**Outcome:** native capabilities improve common collection workflows without platform lock-in.

- Camera/photo picker: prefer standard file inputs with `accept=image/*` and optional `capture`; offer conventional picker fallback. The API sends a `Permissions-Policy` with `camera=()`; a file input with `capture` is unaffected, but `getUserMedia` on the app's own pages would be blocked, so the shell response would need a different policy before any in-page camera preview.
- Web Share API for sharing supported item/collection links; fallback to copy link.
- Optional Web Share Target for receiving shared URLs/images into quick capture, where supported; treat as an enhancement and design POST payload handling carefully.
- Manifest shortcuts for `Quick capture`, `New item`, `Search` using stable frontend routes.
- Clipboard integration and optional vibration feedback only where appropriate and supported.
- Consider badge API and notifications later, not as prerequisites.

**Acceptance:** quick capture works from installed app, shortcuts reach authenticated routes safely, and unsupported integrations have accessible fallbacks.

### Stage 5 — App shell resilience and updates

**Outcome:** deployed changes are reliable and the app gives a useful experience when the network disappears.

- Cache immutable build assets with revisioned names; avoid caching authenticated API responses.
- Network-first navigation with a generic offline fallback for failed navigation requests.
- Keep auth endpoints, private media, admin routes and API responses out of service-worker caches initially.
- Show clear offline status and explain that data operations require connectivity.
- Surface an update-ready prompt where appropriate; avoid `skipWaiting()` on an active editing session without user coordination.
- Ensure old clients can tolerate rolling deployments, with API compatibility expectations.
- Provide explicit cache cleanup, service-worker migration and recovery paths.

**Acceptance:** an offline launch displays an intentional shell/fallback; no private API content is stored in Cache Storage; updates do not silently discard unsaved form state.

### Stage 6 — Advanced platform polish (optional)

**Outcome:** further native-like affordances without creating hard dependencies.

Evaluate launch handling, protocol/file handlers where supported, platform-specific icon variants, badges, push notifications, and optionally TWA/Capacitor packaging only if distribution requirements justify the complexity. Do not assume iOS and Android support the same APIs.

## 4. Future design: offline data and synchronisation

**Explicitly out of scope for the stages above.** Reserve interfaces now; implement when real user stories justify it.

Candidate architecture:

```text
SvelteKit views
  → repository abstraction (remote now; local-aware later)
  → IndexedDB local read models + pending operation queue (future)
  → sync coordinator (future)
  → existing FastAPI application use cases
```

Future design decisions:
- Define which entities and media can be cached per signed-in user and collection permissions.
- Use server-generated change cursors or timestamps with stable ordering, deletion tombstones and pagination.
- Idempotent mutation IDs, replay semantics and conflict policy (do not default blindly to last-write-wins).
- Permission revocation, logout and account switching must invalidate local private data.
- Handle quota eviction, partial media downloads, schema upgrades and interrupted sync.
- Prefer foreground sync first; background sync is not universally available.
- Assess local encryption and realistic device compromise threat models before storing sensitive data offline.

Avoid implementing a generic sync engine during initial PWA work.

## 5. Cross-cutting decisions

### Security and authentication
- HTTPS in production and restrictive CSP compatible with manifest/service worker registration.
- Scope service worker to intended application paths; avoid unexpected cross-app control.
- No secrets in manifest, static assets, or service-worker source.
- Respect existing session expiry and refresh-token flows on installed launches.
- Test cross-origin API setups: same-origin routing is preferable for simpler PWA behaviour.
- Review CSRF and upload handling before adding a share-target POST endpoint. Unsafe cookie-authenticated requests must pass `verify_csrf` (`Sec-Fetch-Site`/`Origin` from the site's own pages), and an OS share sheet posts cross-site, so a share target needs a deliberate exemption or a different handoff design.

### Configuration and ownership
- Separate public PWA branding from private administrative settings.
- Reuse the existing tunable settings (`Tunable()` fields on settings groups, edited on the admin settings page); do not duplicate configuration state.
- Define backend schema and public projection before UI configuration is built.
- Ship default icons/manifest first; editable icons can follow dynamic text/colour settings.

### Service-worker implementation
- The current SvelteKit adapter is static and emits `200.html`; do not assume an `index.html` SPA fallback or a runtime SvelteKit server.
- A built `service-worker.js` is a real file in the build root, so `SpaStaticFiles` serves it; add the `no-cache` header there (see the routing constraint). A missing file is already a 404, not the shell.
- Prefer a small, explicit worker initially. Evaluate `@vite-pwa/sveltekit`/Workbox only if the added caching and lifecycle complexity is justified.
- Use SvelteKit native service-worker support where sufficient. Serve its generated worker from FastAPI at the expected root URL with JavaScript MIME type and revalidation headers; verify the actual build output and scope.
- Do not blindly precache every generated page, API URL or uploaded image.

### Observability and testing
- Add smoke tests for manifest schema, MIME type, icon accessibility and service-worker headers.
- Test installation, deep links, updates, offline fallback and auth expiry on actual Android Chrome and iOS Safari/home-screen apps.
- Add Lighthouse checks as useful diagnostics, not as a substitute for real-device testing.
- Avoid collecting device fingerprints; diagnostics should be minimal and privacy-conscious.

## 6. Proposed component boundaries

Names are illustrative, not assertions about existing source paths.

```text
frontend/src/lib/pwa/
  capabilities.ts          # feature detection and platform adapters
  install.ts               # install prompt/installation state
  updates.ts               # worker lifecycle and update UX
  connectivity.ts          # online/offline hints, not proof API is reachable
  manifest.ts              # typed public manifest/branding representation

frontend/src/lib/components/pwa/
  InstallPrompt.svelte
  UpdateAvailable.svelte
  OfflineNotice.svelte

backend: public PWA branding schema + read-only projection/manifest endpoint
```

Do not add separate domain services for PWA until offline storage is genuinely required.

## 7. Decisions and trade-offs

| Decision | Recommendation | Trade-off |
|---|---|---|
| Delivery | PWA in existing SvelteKit app | Browser capability differences remain |
| Manifest | Backend-owned dynamic, same-origin URL | Additional endpoint and cache discipline |
| Manifest identity | Stable per installation scope | Requires careful path-based deployment rules |
| Branding | Instance-wide first | Per-user names/icons are harder and can change installation identity expectations |
| Service worker | Minimal shell-only at first | Limited offline usefulness initially |
| Install UX | Contextual, progressive enhancement | iOS requires manual Add to Home Screen flow |
| UI | Mobile-first touch refinements | Additional design and regression testing |
| Sync | Defer until separate HLD | Online connectivity remains required for data |
| Packaging | No native wrapper initially | Some OS integrations remain inaccessible |

## 8. Suggested implementation slices

1. **PWA-00:** Mobile/safe-area/viewport audit and fixes.
2. **PWA-01:** Static manifest, icons, standalone mode and install checks.
3. **PWA-02:** Minimal native SvelteKit service worker, offline fallback and safe update prompt.
4. **PWA-03:** Mobile navigation, transitions and touch/keyboard polish.
5. **PWA-04:** Dynamic FastAPI manifest endpoint, stable identity and cache headers.
6. **PWA-05:** Instance branding settings and icon management (optional split: text first, uploads later).
7. **PWA-06:** Camera/share integration and quick-capture shortcuts.
8. **PWA-07:** Optional advanced integrations and platform compatibility matrix.
9. **Future separate HLD:** Offline storage, mutation queue, sync and conflicts.

Each slice should include focused tests, manual acceptance steps and an independently reviewable PR.

## 9. Open questions

1. Are instances always hosted at the origin root, or must `/menagerist/` path-based hosting be supported?
2. Should the installed name/icon be instance-wide, or eventually user-customisable?
3. *Answered:* `SpaStaticFiles` in `entrypoints/api/spa.py` serves `200.html`; register the manifest route in `application.py` before the `/` mount, and set the worker's cache header in `spa.py`.
4. Which navigation destinations should be available as home-screen shortcuts?
5. Should the offline fallback simply explain connectivity, or display a cached read-only application shell?
6. Which device/browser combinations define the minimum supported experience?

## 10. Recommended first milestone

Ship the mobile baseline and a **static installable manifest first**, followed by the minimal service worker and update handling. Add the FastAPI dynamic manifest and configurable branding only after the install experience works; do not make settings work a prerequisite for installation. Offline domain data and synchronisation remain separate future work.
